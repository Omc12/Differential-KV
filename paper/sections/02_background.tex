\section{Background and Motivation}
\label{sec:background}

\subsection{The KV-cache memory arithmetic}
Consider a decoder-only transformer~\cite{vaswani2017attention} with $L$ layers, $\Hkv$ key/value
heads (grouped-query attention~\cite{ainslie2023gqa} shares each KV head across several query
heads), and head dimension $\dhead$. Caching
one token's keys \emph{and} values across all layers, in fp16, costs
\begin{equation}
  b_{\text{tok}} \;=\; 2 \cdot L \cdot \Hkv \cdot \dhead \cdot 2\ \text{bytes}.
  \label{eq:tokbytes}
\end{equation}
For our evaluation model (Qwen2.5-1.5B: $L{=}28$, $\Hkv{=}2$, $\dhead{=}128$) this is
$28{,}672$ bytes per token---about $28$\,KB. The cache for a sequence of length $N$ is therefore
$N\cdot b_{\text{tok}}$ and grows without bound in $N$: $16$k tokens cost $0.47$\,GB, $32$k cost
$0.94$\,GB, and $64$k cost $1.8$\,GB. Against $8.6$\,GB of unified memory shared with the weights
($\approx 1$\,GB at int4), the OS, and transient prefill activations, the cache is the term that
decides whether a long context fits.

\subsection{The design space}
Three broad families shrink the cache. \emph{Quantization} stores $K$/$V$ at lower precision
(e.g.\ int4/int8, per-channel or per-token scales)~\cite{liu2024kivi}; it is simple and preserves
every token, but uniformly low precision erodes the outlier tokens most. \emph{Eviction /
selection} keeps only a subset of tokens---attention sinks~\cite{xiao2024streamingllm}, heavy
hitters~\cite{zhang2023h2o}, persistence-of-importance~\cite{liu2023scissorhands}, prompt-aware
selection~\cite{li2024snapkv}, or query-aware block retrieval~\cite{tang2024quest}; it can be very
compact but risks discarding a token that a later query needed. \emph{Low-rank factorization}
exploits redundancy across tokens or channels, replacing the cache with a small
basis~\cite{deepseekv2,dong2024less}; it compresses the shared structure well but, by construction,
discards the low-energy directions in which distinctive tokens live. Orthogonally, KV \emph{memory
management} such as paged attention~\cite{kwon2023vllm} reduces fragmentation without shrinking the
logical cache, and heterogeneous CPU--GPU inference frameworks such as
kTransformers~\cite{yang2025ktransformers} keep hot operators on the GPU while offloading cold
operators and KV state to CPU memory, extending effective capacity at the cost of host--device
transfer latency. DeepSeek-V2's Multi-head Latent Attention (MLA)~\cite{deepseekv2} takes
a different angle: it re-trains the model to project keys and values into a shared low-rank latent
space at the architecture level, reducing KV cache footprint without post-hoc compression. \dkv{}
draws on both ideas: it adapts kTransformers' tiered CPU--GPU offloading to the compressed-block
level (\S\ref{par:ktransformers}), and incorporates an optional MLA-style latent projection as a
pre-SVD step (\S\ref{sec:impl}), without requiring model re-training.

The tension common to all three is that the tokens most expensive to keep---rare, high-entropy
tokens such as identifiers, digits, and names---are exactly the tokens that verbatim recall
needs, and exactly the tokens a shared low-rank or low-bit code represents worst. A method that
only compresses the shared structure will paraphrase fluently and misquote the one fact that
mattered.

\subsection{Design principle: separate the smooth part from the outliers}
\dkv{} responds to that tension directly by splitting each block into two representations
with complementary strengths. The bulk of a block---the smooth, correlated variation shared by
its tokens---is captured by an anchor and a rank-\rank{} joint $K\!\mid\!V$ delta, which is cheap
and reconstructs the shared structure at low error. The residual outliers---the handful of rows
the low-rank basis reconstructs worst---are kept \emph{exact}. Because the residuals are chosen
by measured reconstruction error rather than by a hand-picked token class, the mechanism is
content- and model-agnostic: it keeps whatever a given block's distinctive tokens happen to be.
The recent past is not compressed at all; it lives in a small exact recency window, so
short-range attention is always faithful. \S\ref{sec:eval} shows that this split is what lets a
buried passcode survive compression exactly (E5) while the low-rank part keeps the per-block
budget small.

\subsection{Unified memory and MLX}
Our target is Apple silicon, where the CPU and GPU share one physical memory pool. This changes
the accounting in two ways that shape the implementation. First, there is no host--device copy:
a tensor produced on the GPU is visible to NumPy without a transfer, so the randomized SVD used
during compression can run in NumPy on the CPU while the attention kernels run on the GPU, with
no marshalling cost. Second, ``freeing'' memory means returning it to a single shared pool that
the rest of the system is contending for, so bounding \emph{peak} allocation matters as much as
bounding steady state. \dkv{} is built on \mlxe{}: it monkey-patches the attention of an
\texttt{mlx\_lm} model, keeps its compressed store in \mlxe{} fp16 arrays, uses a persistent fused
decode buffer, and explicitly releases the prefill cache at the prefill$\to$decode boundary
(\S\ref{sec:runtime}).

\subsection{Discrete GPU memory model}
\label{sec:background-cuda}

\begin{\figenv}[t]
  \centering

  silicon the CPU, GPU and NPU address one physical DRAM pool, so a tensor crosses no

  system shares. \emph{Right:} on a discrete GPU, HBM is a separate physical pool behind

  \label{fig:memtopology}
\end{\figenv}

On discrete-GPU hardware (NVIDIA \cuda{}) the memory model differs from unified memory in two ways
that directly shape implementation choices (Figure~\ref{fig:memtopology}).

\paragraph{Separate HBM pool.}
The GPU's High-Bandwidth Memory (HBM) is a distinct physical pool from host DRAM. Any
tensor crossing the boundary incurs an explicit PCIe host--device (H2D) or device--host (D2H)
transfer. For \dkv{}'s block-level CPU--GPU offloading, a default block
(${U}$: $63{\times}32$ int8; ${V_K,V_V}$: $2{\times}32{\times}\Hkv{\times}\dhead$ fp16;
anchors/residuals: fp16) totals $\approx137$\,KB, costing $\approx15\,\mu$s on PCIe~4.0.
At decode cadences of $20$--$80$\,ms per token this is below $1\%$ overhead even for a cold
hit---and the step-ahead async prefetch (\S\ref{par:ktransformers}) hides it entirely by
issuing H2D restores a step ahead via a dedicated \texttt{cudaStream}.

\paragraph{Compression on a discrete GPU.}
On \mlxe{} the randomized SVD runs in NumPy on the CPU at near-zero marshalling cost
(unified memory). On a discrete GPU, the same CPU SVD is still available but incurs a D2H copy
of the raw $K/V$ block at compression time---acceptable as a one-time prefill cost per block.
A GPU-native path uses the \emph{Gram-Eigh reformulation}: computing the $r{\times}r$
symmetric Gram matrix $B B^\top$ and calling \texttt{cuSOLVER} \texttt{syevjBatched}, which
batches correctly for $r{\le}32$ (unlike \texttt{gesvdjBatched}, which falls back to a
sequential loop for matrices larger than $32{\times}32$).
Controlled CPU measurements show this reduces compression time from $\approx6.1$\,s to
$\approx2.6$\,s per representative prefill; GPU recall validation is pending
\pendingGPU{} (\S\ref{sec:impl}).
